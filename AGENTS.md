# Beyond ESBuild instructions

Beyond ESBuild is a fork of evanw/esbuild for Beyond's modular compilation and package-distribution contracts. Read [the project guide](docs/README.md), [setup](docs/setup.md) and [Beyond architecture](docs/beyond-architecture.md) before changing assessment contracts. The root README introduces Beyond ESBuild; the [upstream introduction](docs/upstream.md), compiler source layout, public APIs and MIT attribution are preserved.

- Independent Git repository; local coordinated work uses `feature/next`. Preserve working changes and upstream history. No commits, pushes, package publication or consumer migration without explicit authorization.
- Follow [coding standards](docs/coding-standards.md) for new Beyond code. Upstream/vendor/generated code remains exempt; do not rewrite it to match Beyond conventions.
- Keep documentation in English and self-contained. Keep fixtures, build adapters and executable tests in `beyond/`, separate from documentation. Generated output belongs under ignored `beyond/.cache/`.
- Keep repository content portable: never hardcode a developer's physical checkout, home, temporary-toolchain or private agent-runtime path in first-party documentation, instructions, code, fixtures or versionable reports, including `docs-temp/`. Use repository-relative paths, documented configurable variables or neutral placeholders. Runtime-resolved paths may appear in ignored local diagnostics; sanitize them before copying evidence into repository content.
- Keep tests discoverable and their examples readable, as [the testing guide](beyond/README.md#tests-fixtures-and-generated-output) describes for this repository: it names each test level, its command, prerequisites, fixtures and what a pass establishes. Contract/unit and integration tests live in `test/` or `tests/`, complete journeys in `acceptance/`, harness infrastructure in `support/`. Applications, packages, modules and documents a test exercises are checked-in files with their real extensions under the consuming area's `fixtures/`, each group with a README naming its entry modules and expected behavior; the harness copies them to a unique temporary directory, substitutes only explicit values such as versions or ports, and never writes the originals, even on failure. Keep inline only small input values, short edits and protocol payloads; generate source only when generation is the behavior under test (size, combinations, malformed input), with the reason and how to reproduce and inspect it in the guide. Fixtures stay out of production compilation and packaging, and migrating a test keeps its positive, negative and recovery cases and its real execution path.
- Describe the current delivery accurately: fixtures and tests use existing compiler APIs and explicit adapters plus one opt-in compiler change, assigned CommonJS exports; upstream behavior is unchanged when the option is off. The [packaging guide](docs/packaging.md) records the packaging mode, its adapters, the pinned package coverage and the bounded Packages trial; the option above is needed only for creators, not for packaged output. Packaged-mode HMR, Packages adoption and production integration remain open. Documentation corrections do not start the next implementation task.
- Preserve distinct internal-source, public-module and package/version graphs and bare public identities. Follow [execution modes](docs/execution-modes.md): esbuild packaging does not require runtime internal creators; unified-runtime composition does. Per-module development selection and packaged-mode HMR are requirements, not outcomes proven by legacy creator fixtures.
- The public module is the only unit of executable division. In `beyond/packaging/` compile every public module on its own: do not enable code splitting, emit private chunks, compile several entries together, publish private files as public modules or merge distinct public modules. A package whose public modules share private files is reported as unsupported until a solution compatible with [public module identity](docs/execution-modes.md#public-module-identity-and-shared-implementation-files) exists; keep cases B1–B3 and E6 of [the packaging guide](docs/packaging.md#shared-state-between-public-modules) passing.
- Fork-specific compiler code is marked `Beyond ESBuild` and documented in [assigned CommonJS exports](docs/cjs-exports.md). Keep such changes opt-in and leave upstream output, runtime helper order and upstream test snapshots unchanged; regressions live in `internal/bundler_tests/bundler_beyond_test.go` with their own snapshot file. Rerun every Go test package and `beyond/prepare.mjs` after a compiler change.
- Build and test the checked-out compiler. Label source observations, executed evidence, adapter behavior and unknowns separately. Necessary targeted compiler changes for external packages, Beyond internal composition or graph traversal are authorized. Establish the failing contract and assess existing public APIs/adapters first; preserve public compatibility and add relevant regressions. Broad unrelated rewrites remain unjustified.
- Read [assessment instructions](beyond/AGENTS.md) for that subtree. Record exact toolchain, source revision, command and limits for claims of compatibility. Browser behavior requires actual browser execution; CommonJS requires a compatible runtime.
- Keep the two paths distinct: Beyond-authored creator composition and packaging existing external libraries. React browser/SSR and Express Node tests validate different contracts. System.register is an explicit adapter output, not native esbuild support.
- Modular CSS belongs to public module/artifact identity and runtime adoption. A CSS bundle alone does not validate style registration, shadow-root application or dependency invalidation.
- Read [documentation instructions](docs/AGENTS.md) before editing guides. Keep durable maintained documentation in `docs/` and temporary handoffs/plans in `docs-temp/`. Preserve lasting decisions in canonical guides before retiring temporary material; canonical onboarding must not depend on disposable handoffs. Preserve upstream architecture/development documents and place Beyond-specific contracts in separate guides.
