# Compiler audit for Beyond ESBuild

Baseline: upstream commit `f6058f8364fe7ab91ca57a83e02577ed74c9cae4`, inspected locally on 2026-09-18. All coordinates below are repository-root paths at that commit. [Upstream source at the baseline](https://github.com/evanw/esbuild/tree/f6058f8364fe7ab91ca57a83e02577ed74c9cae4) supplies immutable coordinates; local `beyond/` additions are separate uncommitted work.

The public API provides useful extension points for Beyond's first creator adapter without changing the compiler. A standard ESM bundle alone cannot establish Beyond's internal identities, creator replacement semantics or public/package graph contracts. [Requirements](requirements.md) traces these contracts to Beyond consumers; [the capability workspace](../beyond/README.md) and its example hold the executable work.

## Traced pipeline and extension boundaries

1. `lib/npm/node.ts:135–142` forwards build/context/transform to the service. `255–286` starts the matching executable with `--service=<version>` and connects a shared protocol channel. `cmd/esbuild/service.go:203–284` dispatches build/transform/resolve/rebuild requests. This is a process boundary; changing a Go API result does not automatically expose it to JavaScript. A future result-schema change must also cover both protocol implementations, shared types and service serialization.
2. `pkg/api/api_impl.go:901–977` validates a context, installs plugins once and creates reusable caches. `984–1068` coordinates an active rebuild; concurrent rebuild callers can share a result. `1488–1575` creates the per-build filesystem, calls `bundler.ScanBundle`, then `Bundle.Compile(..., linker.Link)` if scanning succeeded, and converts output into public results. This is compiler scheduling, not a Beyond publication/HMR transaction.
3. `internal/js_parser/js_parser.go:1–95,17815–17885` shows two passes: parse/scopes/declarations, then binding/folding/lowering. The lexer is called as parsing proceeds. Parsed imports already reflect language handling and transformations; an authoring graph cannot be reconstructed by treating the emitted runtime graph as complete. `internal/ast/ast.go:15–180` explicitly marks some imports unused and distinguishes import statements, require, dynamic import, require.resolve and CSS references.
4. Resolution combines esbuild's filesystem/package rules with ordered plugin hooks. `internal/resolver/resolver.go:368–465` applies aliases and external/URL/builtin handling; `package_json.go:1–75` carries package main/browser/side-effect/import-map data. `internal/bundler/bundler.go:1052–1135` gives plugins importer, path, kind, attributes, resolve directory and plugin data; the first successful hook controls the result. This is the appropriate initial seam to preserve public bare identities and attach Beyond-selected metadata. Esbuild's package path or source index is not Beyond's package/version/public-module identity.
5. `internal/bundler/bundler.go:2176–2251` drains parsed dependencies, schedules nonexternal inputs and records external paths. Traversal is conditional on bundle mode. Per-file transform alone therefore does not resolve the full graph. `3037–3125` obtains reachable files, begins source-map work and invokes one linker for splitting or one per entry otherwise.
6. `internal/graph/graph.go:1–160` separates cached input from mutable linker state. It warns that immutable input is shared across links/rebuilds, and that source indices are unstable for ordering. `Link` in `internal/linker/linker.go:227–350` clones the graph, configures CJS/ESM helper references, scans imports/exports, shakes/splits, computes chunks and cross-chunk dependencies, then emits in parallel. A chunk boundary is a linker decision, not a Beyond internal-module boundary. Creator identity must be explicitly owned by the adapter.
7. `internal/js_printer/js_printer.go:4969–5025` prints AST parts with resolved symbols and collects import metadata, legal comments and a source-map chunk. `internal/runtime/runtime.go:209–270` implements export getters, copying/re-exports and CJS/ESM namespace conversion. These semantics must be assessed before exposing generated objects directly to a runtime that deletes/refills exports.
8. `internal/cache/cache.go:1–115` states the immutability and option-key invariants and allocates indices. `cache_ast.go:1–202` reuses an AST only when source and parser options match, including plugin-provided contents. `pkg/api/watcher.go:1–110` uses polling and refreshes tracked paths; `internal/fs/fs.go:1–130` tracks queried entries versus whole directories. None of these systems implements Beyond's client-side creator replacement, reverse-dependency reevaluation, disposal or runtime rollback.

## Findings and bounded decisions for Beyond

| Finding | Evidence and implication | First bounded probe / decision |
| --- | --- | --- |
| Public externalization is an API/plugin responsibility available today | Resolve hooks expose importer/kind and can return an external path. Public options include `Packages`, `External`, `Platform`, `Conditions` and `Format` (`pkg/api/api.go:289–369`). | Preserve same-package public subpaths as bare imports; keep source, public and package/version graphs separate. Do not replace Beyond resolution with npm lookup implicitly. |
| Metafile/resolve observations are compilation evidence, not every authored relationship | Parser flags include unused/type-only imports; scan follows parsed records in bundle mode. Dead branches and type erasure may precede scan. | Compare authored, parsed and emitted cases with unused/type-only imports and computed specifiers before proposing a source-graph API. |
| Whole-bundle output does not preserve creator boundaries by contract | Linker operates on parts, liveness and chunks and may hoist/merge code. | Keep per-internal transformation plus explicit composition as the first adapter. Assert IDs, hashes, public export namespace and runtime execution, not only output text. |
| Generated CJS export descriptors conflict with delete/refill if used directly | `__export`/`__copyProps` define getters without `configurable: true`; `__toCommonJS` creates another object. | Adapt generated exports into the runtime-owned mutable object, then test live values, shape changes, re-exports, cycles and `module.exports` replacement independently. A passing simple adapter is not proof of all cases. |
| A static CJS export name inventory is a different capability from conversion | esbuild has CJS/ESM conversion machinery; inspected public API exposes build/transform results and metadata, not an arbitrary CJS export-name analysis service. | The consumer inventory identifies `cjs-module-lexer`; test its actual recognized patterns and generated esbuild output. Failure to detect a name does not imply esbuild cannot emit ESM. |
| Plugin state must be scoped/reset per build | Plugin setup is retained by context; scanning is parallel; ordered resolve hooks may stop at earlier hooks. | Test edge removal and failure/recovery with adapter state. Do not append forever to a shared dependency set or infer canonical ordering from callback arrival. |
| Compiler rebuild and runtime HMR are independent acceptance layers | Context/cache/watch deal with source/output state. No observed API commits a Beyond runtime graph transaction. | Use explicit rebuild for initial compiler tests; later run the actual Packages path and original live imports before any end-to-end HMR claim. |
| Source maps require composition after creator wrapping | Printer generates mappings for its own emitted text; source-map coordinates use UTF-16 columns (`sourcemap.go:13–29`). | Decode final wrapped mappings for representative positions, including non-ASCII source, rather than checking only filenames. |
| New compiler hooks would cross multiple coupled layers | Internal scanner/linker/AST types are Go-internal, cached and concurrently used; JS callers cross a versioned service protocol. | Only propose a minimal hook after a failing supported-API fixture demonstrates need. Preserve immutable ASTs, deterministic output and protocol/version alignment. Necessary compiler-core fixes are authorized for these acceptance cases; this source observation alone does not demonstrate that one is needed. |

No general upstream reorganization is needed for this workspace: parser, resolver, linker, runtime and public API already have separate responsibilities. The bounded `beyond/` area preserves upstream layout and makes future differences reviewable. Retaining upstream Go module/package identity avoids an unrelated import-path migration.

## Current Packages usage audit: three distinct responsibilities

Follow-up inspection on 2026-09-18 read `packages/AGENTS.md`, searched the entire current first-party Packages tree for `esbuild`, `metafile` and `cjs-module-lexer` (excluding `.git`, installed `node_modules` and lockfile noise), and read the callers and graph consumers below. Baseline is Packages `593b9f1cffb8af2e972af7030fd7a7ac8883af96`; its checkout has existing local changes. In particular, `modules/sdk/conditional/esm/assembler.ts` and `package.json` are working-tree sources. This is source evidence, not execution of Packages services or confirmation of the implementation selected by a live loader.

The code confirms that Packages already has external bundling, Beyond internal-module composition and dependency-graph responsibilities. The inspected active implementations do **not** show esbuild as the direct implementation of all three. This distinction describes the current paths without treating their architecture as missing or reopening the intended esbuild direction.

The helper remembered by the user is concretely present as **`cjs-module-lexer`** in both active exports and TS analyzer paths. Its role is static export/re-export discovery from emitted CommonJS, feeding Beyond's public facade/assembly. The TS analyzer explicitly supplements it for ordinary `require` dependencies. It is not an ESM emitter, a package/version resolver or proof that esbuild lacks ESM support. The inspected wrapper's default-only external import assumption and snapshot named exports are consumer adaptation choices; the new React/Express probes exercise explicit facades/bridges instead of changing compiler semantics.

No `metafile` consumer was found in the current first-party Packages search. That observation does not negate existing graphs, esbuild's internal scan, plugin observations, or architectural direction. A future integration should join the appropriate source/public/package layers and preserve their separate semantics; replacing all graph handling with a single compiler graph would lose existing version and public-module validation.

Necessary bounded compiler functional fixes are now authorized by the owner when an actual acceptance failure requires them. The implemented creator, React and Express adapters do not yet demonstrate such a necessity. General consumer migration, commits, pushes and publication remain outside this work. The React/Express guides describe preserved core state as an outcome, not a prohibition on a justified fix.
